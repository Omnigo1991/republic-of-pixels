## 2. Bewertung: Was ist gut

- Der Tech-Stack (Next.js auf Vercel, statisch generiert) ist für ein News-Magazin **die richtige Wahl**: schnell, sicher, SEO-stark, praktisch kostenlos im Betrieb. Kein Rebuild nötig — das Fundament trägt.
- Das Artikel-Datenmodell (`src/lib/types.ts`) ist bemerkenswert vollständig: Kategorien, Plattformen, Tags, TL;DR, "Warum es wichtig ist", Quellen-Array, Review-Struktur. Es ist bereits **pipeline-tauglich** — eine Maschine kann dieses Format befüllen.
- Designsystem und Konzeptdokument sind professionell und konsistent umgesetzt.

## 3. Probleme nach Priorität

### Kritisch

1. **Kein automatisches Publishing möglich (Architektur-Engpass).** Inhalte leben im Code; jede Veröffentlichung erfordert einen Build + Deploy vom lokalen Rechner. Ohne Git-Remote + CI/CD kann keine Pipeline jemals autonom veröffentlichen. → Gelöst durch: GitHub-Repo + Vercel-Git-Integration (Deploy bei jedem Push, automatisch).
2. **Kein Git-Backup.** Bis heute existierte der Quellcode nur als Zip auf dem Desktop. Ein Festplattendefekt hätte das Projekt vernichtet. → Lokales Repo steht seit heute; GitHub-Push ist der nächste Schritt.
3. **Sämtlicher Content ist fiktiv.** Alle 11 Artikel (inkl. "Quellen") wurden im Chat-Projekt als Demo-Inhalte erfunden. Für eine echte News-Plattform ist das ein Glaubwürdigkeits- und Rechtsrisiko (erfundene Zitate/Fakten unter echtem Magazin-Branding). → Die Pipeline ersetzt sie; bis dahin Kennzeichnung oder Depublikation erwägen.
4. **Kein Bildsystem.** Ein Gaming-Magazin ohne echte Bilder wirkt nicht premium und verliert Google-Discover/News-Potenzial (og:image fehlt komplett).

### Hoch

5. **TypeScript-Prüfung war deaktiviert** (`ignoreBuildErrors: true`) — heute behoben, Build ist grün mit strikter Prüfung.
6. **Artikel-Index war hart verdrahtet** — heute behoben: JSON-Dateien werden automatisch erkannt und validiert (Pflichtfelder, Slug-Duplikate).
7. **Kein eigener RSS-Feed** — für ein News-Medium Pflicht (Syndication, Google News, Feedly-Reichweite).
8. **Keine Messbarkeit:** keine Analytics, keine Search Console → Wachstum ist blind.

### Mittel

9. Interaktive Elemente sind Attrappen: Kommentare, Reaktionen, Login, Suche-Overlay (die Suchseite funktioniert client-seitig). Solange sie live sind, versprechen sie Funktionen, die es nicht gibt.
10. `dateModified` = `datePublished` im JSON-LD; Autor ist eine Organisation statt Person (E-E-A-T-Schwäche).
11. Drei tote Vercel-Projekte stiften Verwirrung → archivieren/löschen.

### Niedrig

12. `eslint` ist als Script definiert, aber nicht als Dependency installiert.
13. Zip + Logo-PNG liegen im Repo-Root (Ordnung, keine Funktion).

## 4. Architektur-Entscheidung für die News-Pipeline

**Entscheidung: Git-basierte Pipeline, keine Datenbank (Phase 1).**

```
GitHub Actions (Cron, alle 6 h)
  → RSS-Feeds abrufen (mehrere Quellen)
  → Neue Einträge erkennen (Abgleich mit State-Datei im Repo)
  → Relevanz-Scoring & Auswahl (Claude API)
  → Deutschen Artikel im RoP-Datenmodell generieren (Claude API)
  → Bild beschaffen, prüfen, optimieren
  → JSON + Bild committen und pushen
  → Vercel baut & deployt automatisch (Git-Integration)
  → Log als Actions-Run-Protokoll
```

Begründung gegen eine Datenbank in Phase 1:

- Die Seite bleibt zu 100 % statisch → maximale Performance & SEO, minimale Betriebskosten, nichts kann nachts ausfallen.
- Jeder Artikel ist ein Git-Commit → vollständige Nachvollziehbarkeit, Ein-Klick-Rollback, der Betreiber sieht jede Veröffentlichung als Historie.
- Null zusätzliche Infrastruktur, die ein Nicht-Entwickler warten müsste.
- Publikationslatenz (~2–3 Min. Build) ist bei einem 6-Stunden-Takt irrelevant.

Eine Datenbank (Neon/Postgres) kommt in Phase 2, sobald echte Nutzerfunktionen (Kommentare, Accounts, Admin-Redigieren) gebaut werden — dann mit klarem Nutzen statt auf Vorrat.

**Rechtlicher Hinweis (Pflicht des CTO):** "Bild aus der Quelle übernehmen" ist urheberrechtlich heikel — Fotos anderer Redaktionen dürfen nicht einfach kopiert werden. Die Pipeline priorisiert deshalb **offizielle Presse-Assets** (Publisher-Pressekits, Steam/IGDB-Key-Arts, offizielle Screenshots), die für Berichterstattung freigegeben sind. RSS-Bilder werden nur übernommen, wenn die Quelle es lizenzrechtlich erlaubt. Gleiches gilt für Texte: Die Pipeline generiert eigenständige Artikel auf Faktenbasis mit Quellenlink — kein Umschreiben ganzer Artikel 1:1.
